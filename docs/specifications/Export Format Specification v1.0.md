**Статус:** итоговый документ исследовательского этапа  
**Версия:** 1.0  
**Дата:** 1 августа 2026 г.  
**Область применимости:** исследованный экспорт ChatGPT/OpenAI, содержащий 56 разговоров и 2 244 физических файла `.dat`  
**Назначение:** единый источник истины для последующего проектирования и реализации Chat Archive Explorer

## 0. Нормативный статус документа

Этот документ заменяет все промежуточные исследовательские отчёты проекта:

- `Export Format Analysis.md`;
- анализ графовой модели `mapping`;
- анализ `chat.html`;
- анализ связей сущностей;
- `DAT File Analysis.md`;
- статистический отчёт по 2 244 `.dat`;
- отдельные таблицы и рабочие выводы, сформированные в ходе исследования.

При расхождении между этим документом и любым промежуточным отчётом приоритет имеет **настоящая спецификация**.

В частности, настоящая версия устраняет устаревший ранний вывод об отсутствии ветвлений. Повторное полное исследование доказало наличие альтернативных ветвей в 29 разговорах, 84 узлов с несколькими детьми и 145 листьев.

### 0.1. Нормативные термины

В документе используются следующие уровни достоверности.

**Подтверждённый факт** — утверждение, непосредственно проверенное на полном исследованном наборе или на всех относящихся к утверждению объектах.

**Наблюдение** — закономерность, обнаруженная в исследованном экспорте, но не доказанная как универсальная гарантия всех экспортов ChatGPT.

**Ограничение исследования** — граница метода, набора данных или разрешённых операций, из-за которой более сильный вывод сделать нельзя.

**Открытый вопрос** — аспект, который не удалось закрыть фактическими данными и который может потребовать проверки на другом экспорте или другой версии формата.

**Архитектурный инвариант** — правило проектирования импортёра и внутренней модели, безопасное даже при появлении новых полей, ролей, типов контента или файловых форматов.

Термины **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT** и **MAY** используются в инженерном смысле:

- **MUST** — обязательное требование для корректной и устойчивой реализации;
- **MUST NOT** — запрещённое допущение или действие;
- **SHOULD** — рекомендуемое поведение, от которого можно отступить только по обоснованной причине;
- **MAY** — допустимая необязательная возможность.

# 1. Цель и область исследования

## 1.1. Цель

Цель исследования — установить фактическую логическую и физическую модель экспорта ChatGPT, достаточную для проектирования локального архиватора, который:

- корректно восстанавливает разговоры и альтернативные ветви;
- не теряет сообщения, структурированный контент и метаданные;
- связывает логические вложения с физическими файлами;
- не зависит от HTML-представления OpenAI;
- переносит данные во внутреннюю модель, независимую от конкретной версии экспорта;
- сохраняет неизвестные структуры для будущей совместимости.

## 1.2. Исследованный набор

Полностью исследованы следующие файлы:

| Файл | Роль в экспорте |

| `chat.html` | Самодостаточный просмотрщик, встроенная копия разговоров и таблица привязки assets |
| `conversation_asset_file_names.json` | Имя физического `.dat` → исходное имя файла |
| `export_manifest.json` | Реестр физических и логических файлов, ожидаемые размеры |
| `library_files.json` | Метаданные файлов библиотеки ChatGPT |

## 1.4. Ограничения метода

1. Исследован один конкретный экспорт одной учётной записи. Универсальность полей для всех исторических и будущих экспортов не доказана.
2. Статистическая классификация всех 2 244 `.dat` выполнялась по первым 32 байтам, размеру и SHA-256. Архивы не извлекались, документы не открывались, изображения не декодировались.
3. Подтипы plain text нельзя надёжно определить только по magic number.
4. ZIP-family нельзя надёжно разделить на ZIP, DOCX, XLSX и PPTX только по первым 32 байтам.
5. Семантика редких внутренних метаданных OpenAI не выводилась без явных подтверждений.
6. Отсутствие конкретной роли, типа контента или поля в этом наборе не означает запрета такого значения в других экспортах.

# 2. Общая модель экспорта

Экспорт представляет собой набор логических JSON/HTML-объектов и физический файловый слой.

```text
ChatGPT Export
├── export_manifest.json
├── conversations.json
├── chat.html
├── conversation_asset_file_names.json
├── library_files.json
├── shared_conversations.json
├── user.json
├── user_settings.json
├── ads.json
└── file-*.dat / file_*.dat
```

Основная логическая цепочка разговора:

```text
Conversation
  ↓ mapping[node_id]
Mapping node
  ↓ message
Message
  ├── author
  ├── content
  └── metadata
        └── attachments[]
```

Основные файловые цепочки:

```text
Message.id
  ↓
chat.html assetsJson[message.id]
  ↓
Physical .dat filename
  ↓
conversation_asset_file_names.json[filename]
  ↓
Original filename
```

и:

```text
Message.metadata.attachments[].library_file_id
  ↓ equals
library_files[].id.id
  ↓
library_files[].file_id + ".dat"
  ↓ verified by
export_manifest.json
```

Эти цепочки частично пересекаются, но ни одна из них не является универсально полной для всех файлов.

# 3. `export_manifest.json`

## 3.1. Назначение

`export_manifest.json` является реестром физически включённых файлов и логических файлов экспорта.

Наблюдаемая форма:

```json
{
  "export_files": [
    {"path": "conversations.json", "size_bytes": 77895251},
    {"path": "file_....dat", "size_bytes": 305471}
  ],
  "logical_files": {
    "...": {
      "files": ["..."],
      "sharded": false
    }
  },
  "manifest_file": "export_manifest.json",
  "version": 1
}
```

## 3.2. Подтверждённые факты

- Манифест перечисляет 2 244 физических `.dat`.
- Каждый из 2 244 файлов фактически присутствовал в загруженных архивах.
- Физический размер каждого `.dat` совпал с `size_bytes` манифеста: **2 244 из 2 244**, расхождений нет.
- Поле `logical_files` поддерживает список физических файлов и флаг `sharded`.
- В исследованном экспорте логические файлы не были шардированы.

## 3.3. Нормативное использование

Импортёр:

- **MUST** использовать `export_files[].path` как авторитетный реестр физического присутствия файла в конкретном экспорте;
- **MUST** сверять фактический размер с `size_bytes`;
- **MUST NOT** считать отсутствие файла ошибкой только на основании ссылки из других JSON до проверки манифеста и состояния library-записи;
- **MUST** быть готов к `sharded: true` и нескольким физическим частям логического файла;
- **MUST NOT** использовать манифест как источник MIME, исходного имени или связи с сообщением: этих данных в нём нет.

# 4. `conversations.json`

## 4.1. Корневая структура

Корневой элемент — массив объектов разговоров.

В исследованном наборе каждый разговор содержит следующие поля:

```json
{
  "conversation_id": "...",
  "conversation_template_id": null,
  "create_time": 1720273728.108111,
  "current_node": "...",
  "default_model_slug": "gpt-4o",
  "id": "...",
  "is_archived": true,
  "is_do_not_remember": null,
  "is_read_only": null,
  "is_starred": null,
  "is_study_mode": false,
  "mapping": {"node-id": {"...": "..."}},
  "memory_scope": "...",
  "pinned_time": null,
  "plugin_ids": null,
  "title": "...",
  "update_time": 1720278305.157252,
  "voice": null
}
```

## 4.2. Поля разговора

| Поле | Тип, наблюдаемый в наборе | Роль |
|---|---|---|
| `id` | string | Основной идентификатор разговора |
| `conversation_id` | string | Второй идентификатор, в данном наборе равен `id` |
| `title` | string | Заголовок |
| `create_time` | number | Unix timestamp, секунды с дробной частью |
| `update_time` | number | Unix timestamp |
| `current_node` | string | Узел выбранной активной ветви |
| `mapping` | object | Граф разговора |
| `default_model_slug` | string/null | Модель разговора по умолчанию |
| `is_archived` | boolean | Архивный статус |
| `is_study_mode` | boolean | Режим обучения |
| `is_do_not_remember` | boolean/null | Настройка памяти |
| `memory_scope` | string/null | Область памяти |
| `conversation_template_id` | string/null | Ссылка на шаблон/режим |
| `voice` | object/string/null | Голосовая конфигурация |
| `is_read_only` | null в наборе | Зарезервированное/непроявившееся поле |
| `is_starred` | null в наборе | Зарезервированное/непроявившееся поле |
| `pinned_time` | null в наборе | Время закрепления, не проявилось |
| `plugin_ids` | null в наборе | Историческое/зарезервированное поле |

## 4.3. Источники истины

- Для идентификации разговора импортёр **SHOULD** использовать `id` как основной исходный ID и отдельно сохранять `conversation_id`.
- Импортёр **MUST NOT** предполагать, что `id == conversation_id` во всех версиях экспорта, хотя в исследованном наборе равенство выполняется полностью.
- Для графа источником истины является `mapping` и `current_node`.
- Для модели конкретного сообщения источником истины является `message.metadata.model_slug`, а не `default_model_slug` разговора.

# 5. Графовая модель `mapping`

## 5.1. Фактическая схема узла

В полном исследованном JSON узел содержит:

```json
{
  "id": "node-id",
  "message": {"...": "..."},
  "parent": "parent-node-id",
  "children": ["child-node-id"]
}
```

Корневой узел имеет `parent: null` и `message: null`.

> Примечание: ранний рабочий отчёт ошибочно утверждал отсутствие `children`. Итоговая проверка всех узлов подтвердила наличие и согласованность `children`.

## 5.2. Структурные показатели

| Показатель | Значение |
|---|---:|
| Разговоры | 56 |
| Узлы | 18 946 |
| Сообщения | 18 890 |
| Корни | 56 |
| Листья | 145 |
| Узлы с несколькими детьми | 84 |
| Максимум детей | 4 |
| Merge-узлы | 0 |
| Потерянные ссылки `parent` | 0 |
| Несоответствия `children` обратному индексу | 0 |
| Несвязанные узлы | 0 |
| Циклы | 0 |

Распределение ветвящихся узлов:

| Число детей | Узлов |
|---:|---:|
| 2 | 80 |
| 3 | 3 |
| 4 | 1 |

## 5.3. Глубина и ветви

Глубина корня принимается равной 0.

| Метрика | В узлах, включая root | В сообщениях |
|---|---:|---:|
| Минимальная длина root-to-leaf | 5 | 4 |
| Максимальная | 2 134 | 2 133 |
| Средняя | 491,648 | 490,648 |
| Медиана | 317 | 316 |

Всего root-to-leaf ветвей: **145**.

## 5.4. Merge-узлы

Merge-узел — узел с несколькими родителями. В исследованном наборе таких узлов нет.

Подтверждение выполнено двумя способами:

1. подсчёт входящих ссылок по `parent`;
2. сравнение явных `children` с обратным индексом по `parent`.

Во всех некорневых узлах входящая степень равна 1. Само поле `parent` является скалярным, а не массивом.

### Нормативный вывод

- Для этого формата импортёр **MUST** поддерживать дерево с альтернативными ветвями.
- Импортёр **MUST NOT** сводить разговор к одному линейному массиву до сохранения полного графа.
- Импортёр **SHOULD** допускать будущую несовместимую эволюцию схемы и валидировать, что родитель действительно один.
- Отсутствие merge в одном экспорте является подтверждённым фактом набора, но не универсальной гарантией будущей схемы.

## 5.5. `current_node`

`current_node` указывает на выбранный конечный узел активной ветви.

Активная цепочка восстанавливается проходом:

```text
current_node → parent → parent → ... → root
```

с последующим разворотом.

В архиве:

| Категория | Узлов |
|---|---:|
| Узлы активных цепочек | 17 637 |
| Узлы альтернативных ветвей | 1 309 |
| Всего | 18 946 |

## 5.6. Визуальная модель

```text
ROOT
 └── A
      └── B
           ├── C1
           │    └── D1  (alternative leaf)
           └── C2
                └── D2
                     └── E2  (current_node)
```

Полный архив должен сохранять обе ветви. Линейный экспорт активной ветви может дополнительно строиться как представление, но не как единственная внутренняя модель.

## 5.7. Валидация графа

Импортёр **MUST** проверять:

- что ключ `mapping` согласован с `node.id`;
- что `current_node` существует;
- что каждый ненулевой `parent` существует;
- что нет циклов;
- что `children`, если присутствует, согласован с `parent`;
- что все узлы достижимы от корня либо помечены как повреждённые/сиротские;
- что корень не интерпретируется как сообщение.

При несогласованности `parent` и `children` источником построения дерева **SHOULD** быть скалярная ссылка `parent`, а исходные `children` должны сохраняться для диагностики. Это правило основано на том, что `parent` непосредственно задаёт принадлежность узла предку и используется `chat.html` для восстановления активной цепочки.

# 6. Сообщения

## 6.1. Наблюдаемая схема

```json
{
  "id": "message-id",
  "author": {
    "role": "user",
    "name": null
  },
  "create_time": 1720273777.391471,
  "content": {
    "content_type": "text",
    "parts": ["..."]
  },
  "metadata": {}
}
```

`metadata` присутствует не у всех сообщений.

## 6.2. Роли

| Роль | Количество |
|---|---:|
| `assistant` | 10 418 |
| `user` | 8 472 |

Иные роли в `conversations.json` этого архива не встретились.

Код `chat.html` предусматривает обработку `tool` и особого `system`-сообщения с `metadata.is_user_system_message`, что подтверждает возможность таких ролей в экосистеме, но не их наличие в исследованном JSON.

### Нормативное требование

Импортёр:

- **MUST** хранить роль как произвольную строку, а не enum только из `user`/`assistant`;
- **MUST** сохранять неизвестные роли;
- **MAY** иметь известные отображаемые категории, но не должен отбрасывать сообщение из-за незнакомой роли.

## 6.3. Идентичность узла и сообщения

В исследованном наборе ключ `mapping`, `node.id` и `message.id` согласованы для узлов с сообщением. Это полезная проверка целостности, но внутренней модели не следует отождествлять Node ID и Message ID как одно поле без сохранения обоих исходных значений.

## 6.4. Время

`message.create_time` — Unix timestamp в секундах с дробной частью. Импортёр **MUST** сохранять исходное числовое значение и нормализованное абсолютное время без потери дробной точности.

# 7. Контент сообщений

## 7.1. Найденные `content_type`

| `content_type` | Количество | Основное поле |
|---|---:|---|
| `text` | 15 260 | `parts` |
| `multimodal_text` | 1 693 | `parts` |
| `reasoning_recap` | 984 | `content` |
| `thoughts` | 953 | `thoughts` |

## 7.2. `text`

```json
{
  "content_type": "text",
  "parts": ["строка", "другая строка"]
}
```

- `parts` является массивом.
- Массив может содержать пустые строки.
- Нельзя предполагать, что содержимое всегда находится только в `parts[0]`.
- Markdown и кодовые блоки обычно находятся внутри строкового текста, а не в отдельном обязательном AST.

## 7.3. `multimodal_text`

```json
{
  "content_type": "multimodal_text",
  "parts": [
    "текст",
    {
      "content_type": "image_asset_pointer",
      "asset_pointer": "...",
      "size_bytes": 12345,
      "width": 1024,
      "height": 768,
      "metadata": {}
    }
  ]
}
```

Обнаружено 1 998 частей `image_asset_pointer`.

Структурированные части не являются строками и не должны преобразовываться в текст с потерей полей.

## 7.4. `reasoning_recap`

```json
{
  "content_type": "reasoning_recap",
  "content": "..."
}
```

У объекта нет обязательного `parts`.

## 7.5. `thoughts`

```json
{
  "content_type": "thoughts",
  "source_analysis_msg_id": "...",
  "thoughts": ["..."]
}
```

Это отдельная структура с потенциальной ссылкой на другое сообщение.

## 7.6. Аудиотранскрипция

`chat.html` содержит поддержку части:

```json
{
  "content_type": "audio_transcription",
  "text": "..."
}
```

Такие части в исследованном `conversations.json` не найдены. Это наблюдение о возможностях HTML-шаблона, а не подтверждённая структура текущего набора.

## 7.7. Нормативная модель контента

Импортёр:

- **MUST** диспетчеризовать обработку по `content_type`;
- **MUST NOT** требовать `parts` для каждого типа;
- **MUST** сохранять исходный объект контента целиком;
- **MUST** сохранять порядок всех элементов массива `parts`;
- **MUST** различать строковые и структурированные части;

# 22. Архитектурные инварианты

Ниже приведён нормативный набор правил, на который разрешается опираться при проектировании Chat Archive Explorer.

## 22.1. Инварианты источников данных

1. `conversations.json` является первичным источником логической структуры разговоров.
2. `chat.html` является производным представлением и дополнительным carrier `assetsJson`, но не первичным источником.
3. `export_manifest.json` является источником физического присутствия и ожидаемого размера.
4. Magic signature является источником фактического физического типа при однозначной сигнатуре.
5. MIME и расширение являются метаданными и могут быть ошибочными.
6. `library_files.json` является отдельным каталогом library entities, а не полным реестром сообщений или attachments.

## 22.2. Инварианты внутренней модели

7. Conversation, MappingNode, Message, Content, Attachment, LibraryRecord и PhysicalBlob должны быть отдельными сущностями.
8. Node ID и Message ID должны храниться отдельно, даже если исходно равны.
9. Library `libfile_...` ID и physical `file_...` ID должны храниться в разных namespace.
10. Physical blob не должен владеть логическим именем, provenance или единственной attachment relation; эти свойства принадлежат ссылкам/записям.
11. Дубликаты blob могут объединяться физически, но логические ссылки не могут сливаться.
12. Unknown fields должны сохраняться без потери.
13. Unknown roles, content types, MIME values и metadata types должны быть допустимы.

## 22.3. Инварианты графа

14. Полная модель разговора должна быть графовой/древовидной, не плоской.
15. Альтернативные ветви обязательны к сохранению.
16. Активная ветвь является отдельным производным представлением через `current_node`.
17. Root с `message: null` не является пользовательским сообщением.
18. Порядок ветви определяется parent relation, а не сортировкой timestamps.
19. Timestamp не должен использоваться для восстановления topology.
20. Импортёр обязан обнаруживать cycles, missing parents, disconnected nodes и inconsistent children.

## 22.4. Инварианты контента

21. `content_type` определяет схему содержимого.
22. `parts` не является обязательным универсальным полем.
23. Порядок частей должен сохраняться.
24. Structured parts не должны сводиться к строке с потерей полей.
25. Отсутствие видимого текста не означает отсутствие содержимого.
26. Исходный raw JSON content должен быть доступен после нормализации.
27. Markdown renderer является presentation concern, а не parser concern.

## 22.5. Инварианты файлов

28. `.dat` — транспортное имя, специальный decoder не нужен.
29. Физический тип определяется независимо от `.dat` extension.
30. Manifest path и actual filesystem должны сверяться.
31. Размер проверяется по actual bytes и manifest.
32. Original filename может приходить из нескольких источников; конфликт не должен уничтожать альтернативные значения.
33. Отсутствие names-table entry допустимо для library-only файлов.
34. Отсутствие payload допустимо для library lifecycle records.
35. Повтор ссылки в `assetsJson` не означает новый physical blob.

## 22.6. Инварианты совместимости

36. Парсер должен быть adapter boundary между OpenAI export schema и внутренней моделью.
37. Внутренняя модель не должна зеркалировать JSON 1:1.
38. Все исходные IDs и raw fragments должны быть доступны для аудита.
39. Ошибка одного разговора или файла не должна останавливать импорт всего архива.
40. Импорт должен формировать diagnostics с severity и source path.
41. Валидатор должен отличать fatal corruption, recoverable inconsistency и unsupported-but-preserved data.
42. Импорт должен быть детерминированным: одинаковый экспорт порождает одинаковые internal IDs/relations либо сохраняет source IDs.

# 24. Архитектурные последствия исследования

## 24.1. Парсер должен быть отделён от доменной модели

Поскольку OpenAI-схема содержит дублирующиеся идентификаторы, version-specific metadata и несколько файловых цепочек, прямое использование JSON-структур как доменных классов создаст жёсткую зависимость.

Следствие: нужен слой `OpenAI Export Adapter`, который преобразует вход в стабильную внутреннюю модель и сохраняет raw source fragments.

## 24.2. Conversation model обязана быть графовой

Плоский `messages[]` не способен сохранить 1 309 альтернативных узлов. Внутренняя модель должна включать nodes/edges, branch metadata и active/current pointer.

Линейная хронология должна вычисляться отдельно для выбранной ветви.

## 24.3. Физическое хранилище должно быть отделено от attachments

2 244 physical files соответствуют 2 160 уникальным SHA-256, а один blob может иметь несколько логических ссылок. Attachment, library record и blob не являются одним объектом.

Следствие: допустима content-addressable blob store, но поверх него должны сохраняться независимые relation records.

## 24.4. Не нужен `.dat` decoder

Физические payloads являются стандартными файлами. Слой files должен:

- читать magic;
- назначать фактический тип;
- хранить исходное `.dat` имя;
- выдавать файл с безопасным original/display name.

## 24.5. Magic важнее MIME

29 ошибок MIME доказывают, что attachment MIME нельзя использовать как единственное основание для декодирования, HTTP Content-Type или расширения выходного файла.

## 24.6. Необходима политика конфликтов и provenance

Одно имя, MIME или размер может быть представлен в attachment, library, names table, pointer и manifest. Система должна хранить:

- выбранное canonical value;
- все source values;
- основание выбора;
- diagnostics при конфликте.

## 24.7. Raw preservation является обязательным

Редкие и будущие поля не должны теряться. Нормализованная модель должна поддерживать `raw_json`/extension bags на уровне conversation, message, content, metadata, attachment и library record.

## 24.8. Renderer не должен копировать `chat.html`

Будущий HTML должен быть собственным представлением полной внутренней модели:

- ветви;
- timestamps;
- roles;
- Markdown;
- structured content;
- attachments;
- citations;
- diagnostics/unknown elements при необходимости.

## 24.9. Импорт должен быть потоковым и отказоустойчивым

Архив содержит десятки мегабайт JSON и сотни мегабайт payload. Архитектура должна избегать обязательного одновременного декодирования всех файлов и должна поддерживать поэтапный импорт, hashing streams и транзакционные checkpoints.

## 24.10. Privacy boundary необходима с первого релиза

`user.json`, settings, hidden metadata и reasoning-like structures могут содержать чувствительные данные. Публичный экспорт должен иметь явную политику включения полей, а не экспортировать всё по умолчанию.

# 25. Рекомендуемая классификация ошибок импорта

| Класс | Пример | Поведение |
|---|---|---|
| Fatal archive error | Невалидный корневой JSON, невозможно прочитать manifest | Остановить импорт архива |
| Conversation-local fatal | Цикл или отсутствующий required mapping для одного разговора | Изолировать разговор, продолжить остальные |
| Recoverable inconsistency | MIME не совпадает с magic, `children` не совпадает с parent | Выбрать канонический источник, записать warning |

| Informational | SHA duplicate, repeated assetsJson reference | Сохранить relations, MAY deduplicate blob |
